# 实现方案

## 1. 目标与范围

第一阶段解决四个核心问题：

1. 搜索并确定公司、学校等地点。
2. 查找地点附近的公交、地铁、电车等公共交通站点。
3. 获取站点线路、方向和可用的运营信息。
4. 在给定出发时间和通勤预算下，找出公共交通可达站点及边界站点。

租房、小区、房源和综合评分在可达性能力稳定后接入。

## 2. 默认产品口径

- 租房场景默认计算“候选住处 → 公司”的工作日早高峰路线。
- 用户可以切换为“公司 → 候选住处”，用于晚高峰或其他场景。
- 总通勤时间包含起点步行、等待、乘车、换乘和终点步行。
- “最远站点”默认指可达站点中与目的地球面距离最远的站点。
- 同时输出时间最接近预算的边界站点，避免单一“最远”指标误导用户。
- 可达性与出发日期、时间、方向、交通方式和步行限制绑定，不能作为永久静态结果。

## 3. 总体架构

```text
Web 应用
  │
  ▼
业务 API ─────────────── PostgreSQL / PostGIS
  │                              │
  ├── 地图供应商适配层 ─────── 地图 API
  │
  └── 可达性任务队列 ─────── Worker ─────── Redis
                                   │
                                   └── 可达性计算引擎
```

### Web 应用

负责地点搜索、地图交互、通勤条件表单、任务进度、站点图层、可达区域和路线详情。

### 业务 API

负责请求校验、用户输入标准化、API 密钥保护、任务创建、结果查询、限流和错误归一化。

### 地图供应商适配层

把供应商特有的字段、坐标系和错误码转换为内部统一模型。业务代码不得直接依赖供应商 SDK 返回结构。

### Worker 与可达性引擎

Worker 处理耗时的批量路径规划。可达性引擎只依赖内部接口，负责候选站点筛选、通勤时间计算、边界识别和结果排序。

## 4. 关键业务流程

### 地点与附近站点

1. 用户输入关键词，前端请求地点建议。
2. 用户选择候选地点，后端获取标准经纬度和地点详情。
3. 以地点为中心先查询 500 米内站点，必要时扩大到 1,000～1,500 米。
4. 按供应商 ID、名称、类型和距离合并同一物理站点或多个出入口。
5. 根据真实步行路线排序；API 不支持时暂用球面距离并标注为估算。

### 可达性计算

1. 接收地点、方向、出发时间、时间预算、步行与换乘限制。
2. 生成候选站点集合并去重。
3. 根据地图供应商能力选择算法。
4. 计算每个候选站点的最优路线和总通勤时间。
5. 筛选不超过时间预算的站点。
6. 计算地理最远站点、时间边界站点和各方位边界站点。
7. 返回站点分层、路线摘要和可视化边界。

### 当前 M2 抽样实现

当前部署版先实现无需数据库和任务队列的同步闭环：

1. 按时间预算计算一个受限扫描半径。
2. 从工作地点向 8 个方向生成采样中心。
3. 每个方向调用 POI 周边搜索，并优先选择轨道交通站点。
4. 对去重后的最多 8 个候选逐个调用高德公交路径规划。
5. 对 Web 服务请求做节流、短退避和超时控制。
6. 按 `cost.duration` 筛出预算内站点，再按球面距离确定最远点。
7. 缓存相同地点、方向、日期、时刻和预算的结果 5 分钟。

当前支持由用户选择 1～3 个公司侧接驳站点。每个接驳站点可以进一步限定线路；未选择线路时允许该站全部线路。路径规划以候选居住侧站点和选定接驳站点组成起终点对，请求最多 3 条备选方案并按返回的公交/轨道线路名称过滤。为了控制配额，每轮最多核验 12 个站点组合；选择更多接驳站点时会相应减少地理采样候选数量。

这是一种配额可控的边界抽样，不是连续等时圈，也不保证覆盖城市内所有可达站点。M3 将使用多半径采样、线路图扩展或供应商批量能力提高覆盖率。

## 5. 可达性算法策略

### 优先级 A：供应商公共交通等时圈

如果供应商直接提供基于公共交通的等时圈或可达范围，优先调用并将结果映射到附近站点。这种方式 API 调用最少。

### 优先级 B：公共交通矩阵或批量路线

如果供应商可以一次计算一个起点到多个终点，分批提交候选站点，按总时间筛选结果。

### 优先级 C：逐站点路径规划

MVP 可对每个候选站点请求一次路径规划。必须配置并发上限、重试、超时、取消、任务进度和缓存，避免耗尽配额。

### 长期策略：公交网络图

当供应商提供线路完整站序、站间时间或时刻表时：

- 站点作为节点。
- 相邻站作为乘车边。
- 相邻可换乘站作为步行换乘边。
- 地点到附近站点作为接驳边。
- 使用时间依赖的多源 Dijkstra，在累计时间超过预算时停止扩展。
- 对边界站点再次调用官方路径规划 API 复核。

## 6. API 草案

```http
GET    /api/v1/places/suggestions?q=
GET    /api/v1/places/{providerPlaceId}
GET    /api/v1/transit/stops/nearby
GET    /api/v1/transit/stops/{stopId}
POST   /api/v1/reachability/jobs
GET    /api/v1/reachability/jobs/{jobId}
DELETE /api/v1/reachability/jobs/{jobId}
```

可达性任务请求示例：

```json
{
  "anchor": { "latitude": 31.201, "longitude": 121.587 },
  "direction": "TO_ANCHOR",
  "departureTime": "2026-09-10T08:30:00+08:00",
  "timeBudgetMinutes": 45,
  "maxWalkingMinutes": 15,
  "maxTransfers": 2,
  "modes": ["BUS", "SUBWAY", "TRAM"]
}
```

任务状态统一使用 `QUEUED`、`RUNNING`、`COMPLETED`、`FAILED` 和 `CANCELLED`。

## 7. 领域模型

主要实体包括：

- `Place`：用户选定的公司、学校或其他地点。
- `Coordinate`：统一内部坐标；保留原始供应商坐标系信息。
- `TransitStop`：合并后的逻辑站点。
- `TransitEntrance`：地铁出入口或站点子位置。
- `TransitLine`：线路、方向和运营信息。
- `RouteOption`：一条完整通勤路线及各段耗时。
- `ReachabilityQuery`：一次可达性查询条件。
- `ReachableStop`：站点、最佳路线、通勤时间和距离。
- `ReachabilityResult`：可达站点集合、边界和统计信息。

## 8. 缓存与性能

- 地点建议短期缓存；地点详情和静态站点信息长期缓存。
- 路线缓存键包含起终点、方向、交通方式、限制和出发时间桶。
- 经纬度在不损害准确性的前提下做小范围网格化，合并近似查询。
- 出发时间建议按 5～15 分钟分桶，具体取决于供应商数据精度。
- 优先使用批量接口；逐站请求必须遵守 QPS 与每日配额。
- 前端通过轮询或 SSE 获取任务进度，允许取消过期任务。

## 9. 准确性与风险

- 中国大陆供应商可能使用 WGS-84、GCJ-02 或 BD-09，转换必须集中在适配层。
- 公交搜索结果可能把同一站点的出入口或上下行拆分，需要稳定的合并规则。
- 实时到站、临时停运和首末班信息可能不可用，UI 必须区分实时数据与静态数据。
- 仅用可达站点生成的凹包是“站点覆盖边界”，不应冒充连续、精确的官方等时圈。
- 路线结果受日期、时刻和通勤方向影响，结果页必须展示计算条件和生成时间。
- 地图数据通常有存储、展示和二次加工限制，接入前需确认服务条款。

## 10. 测试策略

- 使用固定地图响应 fixture 测试字段转换和错误归一化。
- 使用小型公交网络测试时间限制、换乘和最短路径边界。
- 对同一物理站点的多出入口、同名站和上下行站做去重测试。
- 在真实城市选择固定样例，与供应商官方地图手工对比路线。
- 增加配额耗尽、限流、超时、部分站点失败和任务取消测试。
